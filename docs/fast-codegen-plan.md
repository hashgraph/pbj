# Fast code generation for PBJ: plan and handbook

This document is the specification for a series of performance improvements to PBJ's generated code and runtime. It
records why PBJ is slower than the protobuf wire format allows, the techniques that close the gap (with reference
code), where each change goes, the option flags, the tests, the benchmark protocol, the pitfalls already found, and
the PR series to build it in.

## 1. Goal and policy

PBJ output must stay byte-identical to protoc for every message (the integration tests enforce this). Within that,
make encoding and decoding as fast as the protobuf wire format allows. Hiero gets every safe improvement by default
and can adopt the rest gradually, per proto file or per message. Latency-sensitive users can turn everything on,
including zero-allocation write and read paths.

| Tier | Rule | How it ships |
|---|---|---|
| A. Safe | No public API change, no meaningful growth of generated code | Always on, no flag |
| B. Bigger code | No API change (or a purely additive one), but noticeably more generated bytecode per message | Opt-in with a `<<<pbj.…>>>` comment on a proto file or message; project default in the `pbj { }` Gradle block |
| C. API | New or changed public API | Opt-in, same mechanism |

"Noticeably more" means: the generated classes of the full HAPI build in `pbj-integration-tests` grow by more than
15% in total bytecode. Measure it in every PR (section 7.4); a change above that goes to tier B.

### The steps

| Step | What | Tier | Flag (comment / Gradle) |
|---|---|---|---|
| 1 | Fast writer: constant tags, inline defaults, direct calls between generated codecs, straight-line size calculation, single-store varint writes | A | none |
| 2a | Parser clean-ups in the existing `parseImpl` | A | none |
| 2b | Byte-array parser with in-order fast paths, used automatically for array-backed input | B | `pbj.fast_parse` / `fastParse` |
| 3 | Back-to-front ("reverse") writer into a reusable buffer: no measuring pass, zero allocation | B (additive API on `Codec`) | `pbj.fast_write` / `fastWrite` |
| 4 | Zero-copy, zero-allocation views over encoded bytes | C (new classes) | `pbj.views` / `generateViews` |
| 5 | Unboxed oneof storage: no `OneOf` object per oneof on parse or construction | C (changes model semantics) | `pbj.oneof_storage = "unboxed"` / `oneofStorage` |

## 2. Why PBJ is slower than it needs to be

A hand-written prototype of "what generated code could look like" for a deeply nested block-stream schema (block
items holding state changes, map keys and values, oneofs at every level, transactions with signatures) produced
exactly PBJ's bytes and was measured against PBJ 0.16.4 driven from its own model objects:

| Operation (per transaction, block of 20,000) | Prototype vs PBJ 0.16.4, AMD EPYC (Zen 5) |
|---|---|
| Write a block | 2.6× faster (no allocation) |
| Parse a block into objects | 2.9× faster, 55% less allocation |
| Read every field without building objects | 5.8× faster, zero allocation |
| Write / parse one transaction | 1.7× / 2.6× faster |
| Read every field of one transaction | 4.7× faster |

The prototype came within about 10% of SBE (a fixed-layout format) for writing. Parsing and reading stayed about
2-2.4× slower than SBE, which is the inherent cost of protobuf's tags, length prefixes and varints. Profiling
(async-profiler with inlining annotations) showed where PBJ's time goes:

- **Writing.** Every field goes through a generic `ProtoArrayWriterTools` helper that takes a `FieldDefinition`.
  The tag varint is recomputed from `field.number()` and the wire type at runtime, and the default and oneof checks
  repeat per field. Nested messages are written through `Codec.measureRecord` / `Codec.write` on the shared `Codec`
  interface. Nearly every message type shares that call site, so the JIT cannot inline it (it is megamorphic). On
  top of that, every message is measured (`protobufSize`, cached in the model) before it is written. PBJ's write
  step alone, with sizes already cached and nothing allocated, cost more than twice the prototype's whole encode.
- **Parsing.** Varints are read through the `ReadableSequentialData` interface. Every nested message sets and
  restores `limit()` inside a try/finally. `Schema.getField(field)` is looked up for every field before the switch,
  although only unknown fields need it. Every oneof allocates a `OneOf`, every bytes field a `Bytes` and every
  repeated field an `UnmodifiableArrayList`.
- **Not the problem: PBJ's varint reader.** `ByteArrayBufferedData.readVar` (the protobuf-java XOR chain) beat an
  8-byte-load-and-mask reader. Keep it; just call it without interface dispatch.

## 3. PBJ architecture you will touch

Read `CLAUDE.md`, `docs/architecture.md`, `docs/code-generation.md` and `docs/codec-protobuf.md` first.

- **Public seam.** `pbj-core/pbj-runtime/src/main/java/com/hedera/pbj/runtime/Codec.java` is an abstract class. The
  public `parse(...)`, `write(...)` and `toBytes` are `final` and call the generated `parseImpl` / `writeImpl`.
  (`writeImpl(T, byte[], int)` has a default implementation that wraps `BufferedData`.) Internal routing, such as
  step 2b's, goes into these final methods without changing the generated API.
- **Generators** are in `pbj-core/pbj-compiler/src/main/java/com/hedera/pbj/compiler/impl/generators/protobuf/`:
  `CodecGenerator` assembles the codec class; `CodecParseMethodGenerator`, `CodecWriteMethodGenerator` (stream
  write), `CodecWriteByteArrayMethodGenerator` (byte[] write) and `CodecMeasureRecordMethodGenerator` produce its
  methods; `LazyGetProtobufSizeMethodGenerator` produces the cached `protobufSize()` in the model. The model itself
  comes from `generators/ModelGenerator`. The intermediate representation is `impl/Field`, `SingleField`,
  `OneOfField`, `MapField` and `FieldType`.
- **Runtime helpers.**
  - `runtime/ProtoArrayWriterTools`: byte[] writes.
  - `ProtoWriterTools`: stream writes.
  - `ProtoParserTools`: `readBytes`, `skipField`, `addToList`.
  - `io/buffer/ByteArrayBufferedData.readVar`: the fast varint reader.
  - `io/buffer/Bytes`: holds the backing `byte[]` and offset.
  - `io/buffer/BufferedData`: a sealed class, either heap `ByteArrayBufferedData` or `DirectBufferedData`.

  `ReadableSequentialData` cannot look at the next byte without consuming it (no peek). That is why in-order parsing
  needs the array path of step 2b.
- **Options.** `impl/LookupHelper` parses `// <<<name = value>>>` comments: the `OPTION_COMMENT` regex, and
  `messageOptionValue(message, option)` for message-level booleans. Its file-level `pbj.java_package` handling shows
  how to read file-level options. `impl/ContextualLookupHelper.generateCopyBuilderTracking` is the precedent for "a
  message comment wins, otherwise the project setting applies". Gradle settings are `Property<Boolean>` fields in
  `pbj-compiler/.../PbjExtension.java`, passed through `PbjCompilerPlugin` → `PbjCompilerTask` → `PbjCompiler` →
  `ContextualLookupHelper`.
- **Tests and benchmarks.** `pbj-integration-tests/` (a composite build of `../pbj-core`) generates the full HAPI
  plus test protos, and the generated test classes compare every message with protoc (bytes, parse, sizes). The
  hand-written tests in `src/test/java/com/hedera/pbj/integration/test/` include `MaxDepthTest`, `MaxSizeTest`,
  `UnknownFieldsTest`, `MalformedMessageTest`, `TruncatedDataTests` and the fuzz test `SampleFuzzTest`. JMH
  benchmarks are in `src/jmh/java/com/hedera/pbj/integration/jmh/`:
  - `ProtobufObjectBench` with `BlockBench` / `EverythingBench` variants, run against protoc;
  - `SampleBlockBench`, over the real block-stream files `src/jmh/resources/*.blk.gz`;
  - `varint/VarIntReaderBench` and `VarIntWriterBench`.

  Earlier results are in `profile-results/`.

## 4. Options design (built in PR 1)

Options use the existing comment syntax. Precedence: a message comment, then a file comment, then the Gradle project
default, then the built-in default.

| Comment (file or message level) | Gradle (`pbj { }`) | Values | Default |
|---|---|---|---|
| `// <<<pbj.fast_parse = true>>>` | `fastParse` | true / false | false |
| `// <<<pbj.fast_write = true>>>` | `fastWrite` | true / false | false |
| `// <<<pbj.views = true>>>` | `generateViews` | true / false | false |
| `// <<<pbj.oneof_storage = "unboxed">>>` | `oneofStorage` | `"boxed"` / `"unboxed"` | `"boxed"` |
| `// <<<pbj.performance = "max">>>` | `performance` | `"default"` / `"max"` (shorthand for all four) | `"default"` |

A message option applies to that message only. Generated code must cope with mixed settings: a fast-parse message
can contain a classic message and the other way round. A message's array parser calls a nested message's array
parser when the nested message has one; otherwise it wraps the nested byte range in a `BufferedData` and calls the
nested message's `parse`. Document the options in `docs/codec-protobuf.md` and `docs/usage-guide.md`.

## 5. Reference code for the techniques

The snippets below come from the prototype, adapted to PBJ names. Generated code should produce the same shape.

### 5.1 Varint writes for byte arrays

**Measured outcome (AMD EPYC, HAPI block items).** The single 8-byte store below, bounded by the message end, lost to
PBJ's unrolled writer by 4-9% in a forward writer; its only win came from writing one-byte varints inline. Exact-size
bulk stores (2, 4 or 8 bytes, or 2 + 1, 4 + 1, 4 + 2, 4 + 2 + 1, as in draft PR #795's `SteinbornBulkByteArray`) beat
both: against the unrolled writer, 23% faster for writes of block items with cached sizes, 15% for freshly built ones
and 12% for `toBytes`; signed transactions were unchanged. They never write past the varint, so they need no `end`
guard. `ProtoArrayWriterTools.writeVarInt` ships them, with the one-byte case inline. The single store is kept below
as "tried; rejected for forward writes", and `VarIntSingleStoreVariantsBench` records the comparison.

Tried and rejected for forward writes:

```java
private static final VarHandle LONG_LE = MethodHandles.byteArrayViewVarHandle(long[].class, ByteOrder.LITTLE_ENDIAN);

/**
 * Writes v as a minimal varint at out[offset] and returns its length. When at least 8 bytes remain before `end`
 * (the end of the message being written, never beyond it), the 7-bit groups are spread into bytes with shifts and
 * masks, the continuation bits set on all but the last byte, and one 8-byte little-endian word stored.
 */
static int writeVarInt64(byte[] out, int offset, int end, long v) {
    if ((v >>> 7) == 0) {
        out[offset] = (byte) v;
        return 1;
    }
    if ((v >>> 56) != 0 || end - offset < 8) return writeUnsignedVarInt(out, offset, v); // existing unrolled writer
    final int size = (64 - Long.numberOfLeadingZeros(v) + 6) / 7; // 2..8
    final long spread = (v & 0x7FL)
            | ((v & 0x3F80L) << 1)
            | ((v & 0x1FC000L) << 2)
            | ((v & 0xFE00000L) << 3)
            | ((v & 0x7F0000000L) << 4)
            | ((v & 0x3F800000000L) << 5)
            | ((v & 0x1FC0000000000L) << 6)
            | ((v & 0xFE000000000000L) << 7);
    final long continuation = 0x8080808080808080L & ((1L << ((size - 1) << 3)) - 1);
    LONG_LE.set(out, offset, spread | continuation);
    return size;
}
```

The store writes up to 7 bytes past the varint. Later fields overwrite them, but `write(T, byte[], offset)` must never
touch bytes past the end of the message, because the caller may own them. Pass the message's end (start offset plus
the measured size) and use the store only when 8 bytes remain before it. Keep the one-byte case inline at every call
site (the call must stay under 35 bytecodes; section 9).

### 5.2 Varint read (keep PBJ's algorithm)

Use `ByteArrayBufferedData.readVar`'s XOR chain over a plain `byte[]` and an int position, with the one-byte case
inline:

```java
long varint() {                       // in the array cursor
    final byte x = in[p];
    if (x >= 0) { p++; return x; }   // under the 35-bytecode inline limit
    return varintWide();              // the XOR chain; the plain loop when fewer than 10 bytes remain in the array
}
```

### 5.3 In-order parsing (step 2b)

Writers emit fields in field-number order. So for each message, first test for each expected tag in turn, then run
the general loop for anything else (out of order, repeated, unknown):

```java
// message Order { uint64 id = 1; fixed64 time = 2; Price price = 3; repeated Leg legs = 4;
//                 oneof kind { Limit limit = 10; Market market = 11; } }
static Order parseArray(ArrayCursor c, boolean strict, boolean keepUnknown, int maxDepth, int maxSize) {
    long id = 0, time = 0;
    Price price = null;
    List<Leg> legs = null;
    OneOf<Order.KindOneOfType> kind = Order.KIND_UNSET;
    // in-order fast path: one predictable byte compare per field
    if (c.at((byte) 0x08)) id = c.varint();
    if (c.at((byte) 0x11)) time = c.fixed64();
    if (c.at((byte) 0x1A)) price = PriceProtoCodec.parseNested(c, strict, keepUnknown, maxDepth - 1, maxSize);
    while (c.at((byte) 0x22)) legs = add(legs, LegProtoCodec.parseNested(c, strict, keepUnknown, maxDepth - 1, maxSize));
    // general loop: identical behaviour to parseImpl (any order, unknown fields, strict mode, last value wins)
    while (c.p < c.limit) {
        final int tag = c.tag();
        switch (tag) {
            case 0x08 -> id = c.varint();
            case 0x11 -> time = c.fixed64();
            case 0x1A -> price = PriceProtoCodec.parseNested(c, strict, keepUnknown, maxDepth - 1, maxSize);
            case 0x22 -> legs = add(legs, LegProtoCodec.parseNested(c, strict, keepUnknown, maxDepth - 1, maxSize));
            case 0x52 -> kind = new OneOf<>(KindOneOfType.LIMIT, LimitProtoCodec.parseNested(c, …));
            case 0x5A -> kind = new OneOf<>(KindOneOfType.MARKET, MarketProtoCodec.parseNested(c, …));
            default -> unknown(c, tag, strict, keepUnknown);
        }
    }
    return new Order(id, time, price, legs == null ? List.of() : freeze(legs), kind);
}
```

Rules learned the hard way:

- **Oneofs stay in the switch.** Copying every oneof alternative into the fast path doubled method size, exceeded
  the JIT inlining budget (`DesiredMethodLimit`) and made parsing slower. Put only scalar fields and non-oneof
  nested fields into the fast path.
- **Repeated fields** loop in the fast path (`while (c.at(tag))`).
- **`parseNested`** reads the length, checks it once against `limit` and `maxSize`, narrows `c.limit`, calls the
  nested codec's array parser directly (a static, monomorphic call), checks that exactly that many bytes were
  consumed, and restores `c.limit`. `maxDepth` is enforced as in `parseImpl`.
- **Presize lists** for consecutive repeated messages by hopping over their lengths without parsing them. Use this
  only for small, cache-hot ranges: counting the elements of a list spanning megabytes was slower than growing the
  list. Above a threshold, estimate the size instead.

The array cursor primitives (`at` must stay under 35 bytecodes):

```java
final class ArrayCursor {
    byte[] in; int p; int limit;
    boolean at(byte tag) {
        final int q = p;
        if (q < limit && in[q] == tag) { p = q + 1; return true; }
        return false;
    }
    int countRepeated(int from, byte tag) {          // consecutive length-delimited fields with this tag
        int q = from, n = 0;
        while (q < limit && in[q] == tag) {
            q++;
            int len = 0, shift = 0; byte b;
            do { b = in[q++]; len |= (b & 0x7F) << shift; shift += 7; } while (b < 0);
            q += len; n++;
        }
        return n;
    }
}
```

### 5.4 Reverse writing (step 3)

This is upb's encoder technique. Write each message back to front, from the end of a buffer the writer owns. A nested
message is written before its length prefix and tag, so its length is simply the number of bytes written since it
began: there is no measuring pass and nothing to shift. Fields and list elements go in reverse order, so the result
reads front to back in field order and is byte-identical.

```java
public final class ReverseBuffer {
    byte[] buf; int pos;                                       // buf[pos..] is the encoded output
    public void reset() { pos = buf.length; }
    int mark() { return buf.length - pos; }                   // bytes written so far; stays valid when buf grows
    void lengthSince(int mark) { varint(buf.length - pos - mark); }
    void ensure(int n) { if (pos < n + 8) grow(n + 8); }      // 8 spare bytes below pos for the 8-byte varint store
    void tag1(int t) { buf[--pos] = (byte) t; }
    void varint(long v) { if ((v >>> 7) == 0) buf[--pos] = (byte) v; else varintWide(v); }
    // varintWide: as 5.1, but the word is stored at pos - 8, shifted left by (8 - size) * 8 bits, then pos -= size.
    // The bytes below the varint are free space in this buffer, so the store is always safe.
}

// generated, fields in reverse order:
static void writeReverse(Order o, ReverseBuffer b) {
    b.ensure(64);
    switch (o.kind().kind()) {
        case MARKET -> { int m = b.mark(); MarketProtoCodec.writeReverse(o.kind().as(), b); b.lengthSince(m); b.tag1(0x5A); }
        case LIMIT -> { int m = b.mark(); LimitProtoCodec.writeReverse(o.kind().as(), b); b.lengthSince(m); b.tag1(0x52); }
        default -> { }
    }
    for (int i = o.legs().size() - 1; i >= 0; i--) {
        int m = b.mark(); LegProtoCodec.writeReverse(o.legs().get(i), b); b.lengthSince(m); b.tag1(0x22);
    }
    if (o.price() != null) { int m = b.mark(); PriceProtoCodec.writeReverse(o.price(), b); b.lengthSince(m); b.tag1(0x1A); }
    if (o.time() != 0) { b.fixed64(o.time()); b.tag1(0x11); }
    if (o.id() != 0) { b.varint(o.id()); b.tag1(0x08); }
}
```

Two refinements: record positions as "bytes written" so they survive the buffer growing, and keep the per-field
`ensure` budgets generous (largest field plus 8).

## 6. The steps in detail

Every step must keep generated code readable (a PBJ principle) and output byte-identical (the protoc comparison
tests). Every speed claim needs before and after numbers (section 7).

### 6.1 Step 1: fast writer (tier A, always on)

Change `CodecWriteByteArrayMethodGenerator`, `CodecWriteMethodGenerator`, `CodecMeasureRecordMethodGenerator` and
`LazyGetProtobufSizeMethodGenerator` so that generated code:

1. **Writes constant tags inline** (`output[offset++] = 0x09;`, two literals for two-byte tags) instead of calling
   `writeTag(output, offset, field, wireType)`. Size code uses a literal 1 or 2 for the tag.
2. **Emits the proto3 default check inline** (`if (v != 0L) { … }`) instead of passing `skipDefault` and
   `field.oneOf()` to a helper. Oneof members are always written; non-oneof scalars, enums, strings, bytes and packed
   lists are skipped when zero or empty, exactly as today.
3. **Calls nested codecs directly.** Give generated codecs package-visible or public `static` entry points (for
   example `static int writeTo(T data, byte[] out, int offset, int end)` and `static int sizeOf(T data)`), and call
   them for nested messages instead of making `Codec<T>` instance calls. The calls become monomorphic and
   inlinable. Messages from another module keep the instance call.
4. **Writes varints with one store** (5.1). Add the runtime helper to `ProtoArrayWriterTools`, with the
   message-end guard.
5. **Keeps helpers small:** anything called per field stays under HotSpot's 35-bytecode inline limit, with slow paths
   in separate methods.
6. **Gets the stream writer (`writeImpl(T, WritableSequentialData)`) the same treatment** for 1-3: constant tags
   via `out.writeByte`, inline defaults, direct calls.

Do not change field order, default skipping, map ordering, unknown-field writing or `protobufSize` caching. API
impact: none.

**Measured (AMD EPYC, PRs #994-#996):** on HAPI block items `write(T, byte[])` became about 30% faster and `toBytes` of
freshly built items 2.1× faster (the plan expected about 2× for both). Block items carry large opaque byte fields
(signed transactions) whose copy cost doesn't change, so deeply nested messages gain more than byte-heavy ones. The
exact-size bulk varint stores (5.1) added 12-23% on top for block items. Code size: tier A grew `*ProtoCodec` classes
by about 10% and all generated classes by about 1.3%, within the 15% limit, instead of the predicted shrink.

### 6.2 Step 2a: parser clean-ups (tier A, always on)

In `CodecParseMethodGenerator` (the existing `parseImpl` over `ReadableSequentialData`):

- Look up `Schema.getField(field)` only in the default (unknown-field) branch.
- Make nested-message handling cheaper: check the length once, and don't set up exception handling per field.
- Leave the behaviour of `strictMode`, `parseUnknownFields`, `maxDepth` and `maxSize` unchanged.

Expected gain: modest (5-15%). Its value is that every Hiero parse gets it, including from streams.

### 6.3 Step 2b: byte-array parser with in-order fast paths (tier B, `pbj.fast_parse`)

For messages with `fast_parse`, generate `static T parseArray(ArrayCursor c, …)` (5.3). Then route in the `final`
`Codec.parse(...)` methods: when the input is array-backed (`ByteArrayBufferedData`, or `Bytes` through
`parse(Bytes)`) and the codec has an array parser, run that parser over `[position, limit)` and advance the input's
position by what it consumed. Streams and direct buffers keep today's `parseImpl`.

`bytes` fields keep PBJ's current semantics: a `Bytes` view or a copy, whichever PBJ produces today. API impact:
none, since the results are the same objects. Code size: about double the parse code of flagged messages.

Also:

- **Nested calls follow #993's rule.** A nested message generated in the same build with an array parser is called
  directly (a static call); otherwise its byte range is wrapped and parsed through its codec. A generated-code test
  checks both, as it does for the writers and `parseFrom`.
- **String fields** use the runtime's shared strict decoder (#1008): `""` for zero length, a Latin-1 string for ASCII,
  otherwise a validating scan, then decoding, with no per-call decoder or buffers.
- **Sparse messages.** Many HAPI messages have many optional fields, few of them present (`TransactionBody`'s wide
  oneof, records, receipts). The in-order fast path pays one failed compare per absent field. Limit it to the leading
  N fields (start with 16), or generate it only where the benchmark data shows a high present-field ratio; measure
  both on block items, transactions and records.
- **Access to the backing array** of `ByteArrayBufferedData` and `Bytes` goes through package-private accessors and
  an internal, unexported bridge, not new public API.
- **Method size.** HotSpot does not JIT-compile methods over 8,000 bytes of bytecode. Put each nested message, repeated
  element and packed-run read in its own small method, called from the fast path and the loop, so large messages stay
  under it.
- **Expected gain, per workload.** Parsing a HAPI block item from `Bytes` was 566 ns; #993 gave 5-11%. Set the target
  from a quick prototype of the array path on `BlockItem` before writing the full generator. (Measured in #1002: block
  items 1.9× faster, whole blocks 2.3×.)

### 6.4 Step 3: reverse writer (tier B, `pbj.fast_write`)

- **Runtime:** add `ReverseBuffer` (5.4), reusable and growable.
- **Generated code:** `static void writeReverse(T, ReverseBuffer)` for flagged messages.
- **New public API (additive, on `Codec`):** `void writeReverse(T item, ReverseBuffer buffer)`. The result is
  available as `buffer.bytes()` (a `Bytes` view over the end of the buffer), `copyTo(byte[], int)` or `toBytes()`.
  Codecs without the flag implement it by measuring and writing forward into the buffer.
- **`toBytes(T)`** may use it internally (reverse write into a pooled buffer, then copy into an exact-size array),
  but only if that measures faster.

In the reverse writer the single 8-byte varint store (5.1) needs no guard: it writes into free space below the cursor,
in a buffer the writer owns. That is where it won in the prototype. Re-measure it there against the exact-size bulk
stores; don't assume either way.

This skips `protobufSize` entirely for objects that are encoded once (for example block items built and written
once), and gives a zero-allocation write path with a caller-owned buffer. Expected gain: 15-20% over step 1 for
deeply nested messages. Keep this step only if it shows at least 10% over step 1 on the decision platform (section
7.3); otherwise drop it from the series.

**Measured (#1003, AMD EPYC, HAPI block items).** On the whole sample block the reverse writer was 1.9× slower than
step 1 even after maps and wrapper types were written in reverse and capacity checks batched, so the fallbacks were
not the cause. Per kind of item, and with the items limited to 200 so they fit in the CPU caches:

| `STATE_CHANGES` | Forward, sizes cached | Reverse | Forward, fresh objects | Reverse |
|---|---:|---:|---:|---:|
| 200 items, in cache | 63 µs | 81 µs (+29%) | 89 µs | 72 µs (−20%) |
| all 21,986 items | 9.2 ms | 39.1 ms (+325%) | 13.8 ms | 39.3 ms (+184%) |

The reverse writer visits each object graph last field first, the opposite of the order the objects were allocated
in. Out of cache that costs 2-4× on EPYC (JFR shows trivial getters such as `OneOf.kind()` at the top of the profile);
on Apple Silicon the same jar shows reverse about equal to forward. In cache it saves the measuring pass, so it is
9-20% faster than step 1 on freshly built objects and 24-29% slower when sizes are already cached. It meets the 10%
bar only for objects encoded right after they are built, so #1003 stays a tier B option, off by default: it is not
used by `toBytes` or the other `write` methods, and its documentation tells users to measure on their own data.
Finding out why HAPI is slow out of cache is follow-up work and does not block merging.

### 6.5 Step 4: zero-copy views (tier C, `pbj.views`)

Generate `XxxView` for each flagged message: a reusable flyweight over encoded bytes that reads fields in place.

- **Wrapping:** `XxxView wrap(byte[] in, int offset, int length)` (and `wrap(Bytes)`) returns `this`. Views are
  reusable, so the steady state allocates nothing.
- **Indexing on `wrap`:** one in-order pass, with the general fallback, records each field's offset in primitive
  fields of the view (last occurrence wins for singular fields). Repeated fields record their first offset and
  count.
- **Scalar and bytes accessors:** scalars decode when accessed. `bytes`/`string` fields expose
  `(array, offset, length)` or a zero-copy `Bytes` slice, plus helpers that avoid allocation (for example
  `xxxEquals(byte[])`).
- **Nested messages:** the parent owns one child view per nested field and re-wraps it on access. Repeated fields
  use a reusable cursor: `for (var it = view.legs(); it.next(); ) { LegView leg = it.value(); … }`.
- **Oneofs:** `kindKind()` returns the generated kind enum; typed accessors return the child view.
- **Validation:** `wrap` validates lengths and wire types and throws `ParseException` on malformed input, with the
  same rules as parse.
- **Conversion:** a `T toModel()` method on each view.

API impact: new classes only. Expected gain: 4-6× over parsing into objects for reading every field, with zero
allocation. This is the path for routing, filtering and hashing selected fields of block items without garbage.

### 6.6 Step 5: unboxed oneof storage (tier C, `pbj.oneof_storage = "unboxed"`)

Today a oneof is stored as a `OneOf<KindEnum>` object, allocated on every parse and construction, and constructors
and builders take it. With the flag, the model stores a kind field and a value field instead:

- **New accessor** `kindKind()` (the existing kind enum). The existing typed accessors (`limit()`, `hasLimit()`,
  `…OrElse`, `…OrThrow`) stay.
- **`kind()`** still returns `OneOf<…>`, but builds it on each call. Document this: its identity is no longer stable,
  and it allocates unless escape analysis removes the object. Hot code should switch on `kindKind()`.
- **Constructors:** the `OneOf` constructor stays and unpacks its argument. Add constructors or builder paths that
  take the value directly, so construction allocates nothing extra.
- **Parsers** (classic and array) set the kind and value directly; writers switch on the kind.
- **Unchanged behaviour:** `equals`, `hashCode`, `toString`, the JSON codec and `protobufSize`.

API impact: the identity and allocation behaviour of `kind()` changes, and accessors and constructors are added, so
this step is opt-in. Measure allocation per operation and parse time.

## 7. Testing and measurement protocol

### 7.1 Correctness, every PR

1. `cd pbj-core && ./gradlew spotlessApply build qualityGate`.
2. `cd pbj-integration-tests && ./gradlew build` runs 100k+ tests, including the generated protoc comparisons.
3. **Run the integration suite a second time with every new option on.** Add a Gradle property (for example
   `-PpbjPerformance=max`, setting `pbj { performance = "max" }`) so that the generated protoc comparisons, the
   MaxDepth, MaxSize, UnknownFields, Malformed and Truncated tests, and the fuzz tests all exercise the new paths.
   CI should run both configurations.
4. **Generated non-canonical-order test, per message** (steps 2b and 4). Take protoc's bytes for each test object,
   reverse the order of its top-level fields and append an unknown field (field 99, varint). Parse, and views,
   must give the same result as for the canonical bytes, and strict mode must reject the unknown field. This is the
   test that catches bugs in the fallback paths (section 9).
5. **Determinism:** written bytes equal protoc's (existing), and for step 3, `writeReverse` output equals `toBytes`
   for every test object.
6. **Mixed options:** a test proto where a flagged message contains an unflagged one, and the other way round.

### 7.2 Allocation tests

Add an `AllocationTest` to the integration tests. Warm up (10k iterations), then measure
`((com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean()).getCurrentThreadAllocatedBytes()` around
10k iterations, and assert:

- **Write to a byte array** (`write(T, byte[], int)`) on an object whose size is already cached: 0 bytes (step 1).
- **Reverse write** (`writeReverse`) into a warmed buffer: 0 bytes (step 3).
- **View `wrap` plus reading every field:** 0 bytes (step 4).
- **Parse:** no more than the result objects. Record the figure per test message and assert it does not grow. With
  unboxed oneofs it must be lower than with boxed ones (step 5).

### 7.3 Benchmarks and the numbers each PR reports

**Decision platform: x86-64 server CPUs (AMD EPYC, Zen 5 class), on an otherwise idle machine.** Decide on these
numbers, and report them in the PR. Other machines, Apple Silicon for example, are fine for iterating but don't
decide anything: results differ between CPUs, sometimes in direction, so confirm every choice on the decision

benchmark machine needs only a Java 25 runtime (`java -jar …-jmh.jar <includes> -f 3 -prof gc -rf json -rff

Report before (the previous PR's branch) against after:

1. **Existing benchmarks.** `ProtobufObjectBench` subclasses (parse and write for the sample block and "everything"
   objects, against protoc); `SampleBlockBench`; `varint/VarIntWriterBench` and `VarIntReaderBench`.
2. **`BlockItemBench`, new in PR 0.** Use every `BlockItem` of the two sample `.blk.gz` block files, measured per
   item:
   - write to `byte[]`, with objects rebuilt before every invocation (`@Setup(Level.Invocation)`; PBJ caches
     `protobufSize`, so reused objects would skip measuring);
   - `toBytes`;
   - parse from `Bytes`;
   - from step 3, `writeReverse`;
   - from step 4, read every field through views.

   Also parse and write the signed transactions found in those blocks on their own. This is the main benchmark for
   the series, because block items are Hiero's hottest serialization path.
3. **GC bias.** Benchmarks that rebuild objects in `@Setup(Level.Invocation)` allocate heavily outside the timed
   region, so young collections tend to happen there, while benchmarks without that setup collect inside it. In
   `BlockItemBench` this made cached `toBytes` look slower than fresh (1,349 against 928 ns with G1; 1,199 against
   1,127 ns with the no-op Epsilon collector). `BlockItemBench` now forks with a 24 GB young generation, so no

   setup instead was tried and made it worse: it evicts the cached objects from the CPU caches, while fresh objects
   were just parsed and are cache-hot. Compare like with like (cached against cached for write-path changes), check

5. **Block files.** Block `…497558` was written with an older `BlockHeader` layout and no longer parses with the

6. **Profiles when a step underperforms.** async-profiler's `ann` option labels frames `_[j]` (compiled), `_[i]`
   (inlined), `_[1]` (C1) and `_[0]` (interpreted), which shows directly which per-field calls were not inlined.

## 9. Lessons already learned (do not rediscover)

- **PBJ's varint reader is good.** The XOR chain beat an 8-byte-load-and-mask reader on both x86-64 and Apple
  Silicon. Keep it; call it without interface dispatch and inline the one-byte case.
- **Varint writes:** in the prototype, single-store varint writes beat the unrolled writer (12-23% for encode). In
  PBJ's forward writer, bounded by the message end, they lost to it by 4-9% on HAPI block items on EPYC, confirmed on
  another workload; the win came only from writing one-byte varints inline. Exact-size bulk stores beat both (5.1).
  The 8-byte store may still win in the reverse writer, where it needs no guard (6.4).
- **HotSpot does not compile methods over 8,000 bytes of bytecode** (`DontCompileHugeMethods`). Generated parsers of
  large messages crossed it and ran interpreted; split per-field work into small methods.
- **HotSpot's inlining limits matter more than micro-optimising arithmetic.**
  - Per-field helpers over 35 bytecodes were not inlined at most call sites ("too big").
  - Large generated methods hit `DesiredMethodLimit`.
  - Copying every oneof alternative into a fast path made parsing slower.

  Keep hot helpers tiny and keep oneofs as a switch.
- **`p += len()` is a bug in Java when `len()` itself advances `p`,** because the left-hand side is read before the
  call. Read the length into a local first. In the prototype this silently broke the fallback path; only the
  non-canonical-order test found it.
- **PBJ caches `protobufSize`.** Benchmarks that encode the same objects repeatedly time only the write, not the
  measuring. Rebuild objects per invocation for realistic encode numbers.
- **Counting the elements of a list that spans megabytes is slower than growing the list,** because of cache misses.
  Estimate instead.
- **Reverse writing beat reserving length bytes.** A forward writer that reserved one byte per length prefix and
  shifted the message when it was wrong needed two-byte reservations for large messages to be competitive (about
  12% faster). Writing in reverse then removed that work entirely (another 15-20%).
- **SIMD is not the lever** for small, branchy messages. Per-field dispatch is the cost.
- **Walking an object graph backward is slow out of cache.** Reverse writing reads fields last first, against the
  allocation order of the objects; on AMD EPYC, with block items that don't fit in the caches, that made it 2-4×
  slower than forward writing. Benchmark object-graph walks both in cache (a few hundred items) and out of it.
- **Don't trust one platform for memory-bound results.** The reverse writer's slowdown didn't reproduce on Apple
  Silicon at all.
- **HotSpot never compiles a method over 8,000 bytes of bytecode.** `TransactionBody`'s stream parser was 15 KB and
  always ran interpreted; splitting messages with more than 32 fields into per-field helpers made it 3.3× faster
  (#1015). `GeneratedMethodSizeTest` keeps every generated method under 7,000 bytes.
- **Unboxed oneofs pay off on parse allocation:** 12-24% less per block item, 13% less per block (#1016).
- **After all of this, most of the remaining parse cost is multi-byte varints of large values** (ids, amounts). That
  is a schema decision (`fixed64` for such fields), not something PBJ can change.
